# 第二阶段实施计划：派出去、收回来

> 状态：草案，待确认后实施。对应[方向文档](2026-09-29_personal-os-direction.md)第 7 节的第 2 步。

## 1. 目标

至少一类任务能稳定地从 Personal OS 派给 Agent，并在 Personal OS 里看到进度、审核结果。

已确认的决定：

- 第二阶段与第一步的 7 天试用同时进行。
- **本机（公司电脑）走直连通道**：由 Personal OS 直接启动本机的 Kimi 和 Claude Code，任务内容和结果都只存在本机。
- **不使用公司内部版 iMultica**，也不使用开源 Multica 的官方云。
- **Multica 通道按开源版编写**，在能使用 Docker 自建服务端的机器上接入和验证。本机不能用 Docker，不在本机验证。
- 顺带完成第一步的两项收尾：来源可点击、在 Obsidian 中核对写回。

## 2. 现状

- **现有派单只支持 Codex，而且本机跑不起来。** `start_agent` 直接调用 `codex exec`，但终端 PATH 里没有 `codex`，只有 `@tencent/codex-internal` 包。所以现在的 Codex 派单、AI 简报和日报整理都不可用。
- **本机可直连的 Agent**：
  - Kimi 0.40.1（`~/.kimi-code/bin/kimi`）：`-p` 非交互执行一条指令，`--output-format stream-json` 输出流式 JSON，另有会话续接和额外目录参数。
  - Claude Code 2.1.199（`~/.local/bin/claude`）：`-p` 非交互执行，支持流式 JSON 输出、权限模式和允许的工具列表。
- **开源 Multica**：Homebrew 安装的 `multica` 0.4.14 尚未配置。
  - 命令行能覆盖所需操作：创建与指派任务（`issue create/assign`）、执行历史（`issue runs`）、执行消息（`issue run-messages`）、取消（`issue cancel-task`）、重跑（`issue rerun`），且支持 JSON 输出。
  - 它必须连一个服务端，任务数据存在服务端，本机守护进程只负责运行 Agent。
  - 自建服务端官方只提供 Docker 和 Kubernetes 两种方式，由 PostgreSQL 17、Go 后端、Next.js 前端组成。
- 本机的 iMultica 是公司内部版，已登录公司内网服务端。本计划不使用。

## 3. 取舍

- **直连通道**：零安装，数据不离开本机，推广给别人时可以装上就用。代价是看板、日志、取消、重试都要 Personal OS 自己实现。每接一个 Agent，都要适配它的命令行参数和输出格式。
- **Multica 通道**：一次接入多种 Agent，还带定时任务等能力。代价是必须有服务端，本机无法验证。

Personal OS 只依赖自己的**运行时接口**，两类通道都挂在接口下面。任务、执行、审核的数据模型归 Personal OS，不依赖任何通道的内部数据。

## 4. 分阶段实施

每阶段结束做一次中文提交。

### 阶段 0：第一步收尾

1. **来源可点击**（H02 遗留）：
   - 会话：点击后在访达中定位原始会话文件。
   - 提交：点击后弹出只读窗口，显示提交说明和改动文件列表（`git show --stat`），不跳到外部网站。
2. **Obsidian 写回核对**（H05 遗留）：写一份核对步骤，由你在 Obsidian 中操作，我根据结果更新验收记录。重点是首页修改后，"纸间 · 首页工作台"插件显示新值，两边交替修改时不互相覆盖。
3. **7 天试用记录**：在验收记录中加一张每日表，记录是否先打开 Personal OS、"上次工作"是否准确、因缺什么而离开。

### 阶段 1：运行时接口

1. 新增 `server/runtime.py`，定义统一接口：检查是否可用、启动、查询状态、读取日志、取消、取结果。
2. 把现有 Codex 调用迁移为第一个直连通道，行为不变。命令路径改为可在设置中填写。
3. 执行记录（`agent_run`）增加三项：使用的通道、通道内的外部编号或会话编号、最近日志。
4. 用一个假通道写测试，覆盖启动、完成、失败、取消、重启后恢复。

### 阶段 2：Kimi 与 Claude Code 直连通道

1. **试跑**：先在一个临时测试目录里，分别手动跑一次非交互执行。确认以下几点：
   - 怎样允许 Agent 在工作目录内改文件、但不越出该目录；
   - 流式 JSON 的事件格式，从中取出进度和最终结果；
   - 退出码的含义；
   - 中途终止后，进程和子进程能否干净退出。
2. **两个通道**：按试跑结果实现，命令路径可在设置中填写。找不到命令时，只把该通道标为不可用，不影响其他通道。
3. **写入范围**：Agent 只在任务所属项目的工作目录内工作。同一目录同时只允许一个执行，沿用现有规则。
4. **提示词**：沿用现有任务提示词（任务、完成标准、项目约束、个人规则），三个通道共用。

### 阶段 3：看板与审核

1. **任务看板**：任务页增加看板视图，按待办、计划中、运行中、待审核、完成、阻塞分列。卡片显示交给了哪个 Agent、运行时长、最近一条日志。
2. **指派**：任务详情里选择 Agent，只列出当前可用的。
3. **执行详情**：显示日志（运行中每几秒刷新一次），可以取消、重试。
4. **审核**：沿用现有审核流程（结果、改动文件、通过 / 退回并补充要求），退回后可以再次派出。
5. 首页提醒条已有待审核、阻塞、运行中计数，这里只核对它能反映新通道的状态。

### 阶段 4：开源 Multica 通道（本机只写不验）

1. 按开源 Multica 的命令行实现运行时接口，不读取 Multica 数据库。Personal OS 的一个任务对应一个 Multica 任务，外部编号记在执行记录上。
2. 设置中新增 Multica 命令行路径和配置档（`--profile`），留空即不启用。
3. 本机只做单元测试：用录制的命令行 JSON 样例驱动。真实接入和验收放到能用 Docker 的机器上。
4. 在 README 中写明自建服务端和接入步骤。

### 阶段 5：验收与文档

写验收记录，更新 README 和方向文档，重建客户端。

## 5. 验收

本机：

| ID | 场景 | 合格结果 |
|---|---|---|
| P01 | 某个 Agent 命令找不到 | 任务页正常；指派时说明原因；其他通道仍可用 |
| P02 | 把项目任务指派给 Kimi / Claude Code | 看板进入"运行中"，能看到日志更新 |
| P03 | Agent 完成 | 进入"待审核"，显示结果和改动文件；通过后完成 |
| P04 | 审核时退回并补充要求 | 带着补充要求再次执行，结果回到待审核 |
| P05 | 运行中取消 | Agent 进程及其子进程停止；任务变为阻塞 |
| P06 | 运行中重启 Personal OS | 重启后标记为中断，并补采改动文件，不留下永远"运行中"的任务 |
| P07 | Agent 尝试修改工作目录以外的文件 | 被阻止，或在审核中明确标出 |
| P08 | 现有计划、任务、审核、日报流程 | 行为不变，现有测试通过 |

体验验收：连续一周，至少一类任务（例如"修一个小 bug"或"写一份调研"）稳定地派出并收回。

另一台机器（Multica 通道）：P02–P05 在 Multica 通道上各做一次；重启后能从 Multica 恢复真实状态。

## 6. 本阶段不包含

勾选完成的自动提示、全局快捷键、手机入口、自动建议交给谁、定时任务、大任务拆分并行。

## 7. 风险

- **命令行格式变化**：Kimi、Claude Code、Multica 升级后参数或 JSON 格式可能变化。对策是记录已验证的版本号，版本变化时提示，参照现有 WorkBuddy 适配的做法。
- **权限边界**：各 Agent 的"允许自动改文件"开关粒度不同，放宽过头可能执行任意命令。试跑时逐个确认，审核环节始终保留。
- **重启后无法续跑**：直连通道的进程随 Personal OS 退出而终止，只能标记中断，由用户重试。
- **Multica 通道本机无法验证**：可能要到另一台机器上才发现问题，因此放在最后一个开发阶段。
- **Codex 内部包**：修复直连路径后，公司内部版本的参数可能和开源版不同，需要实测。
