# Personal OS 项目审查与首次使用指南

审查日期：2026-09-29（Asia/Shanghai）。代码基线：`5205d68`，分支 `main`。

## 结论与范围

当前是**可以开始受控试用的本地个人工作台初版，尚未通过产品 MVP 验收**。每日计划、人工任务、Codex 委派、结果审核、日报和知识提案已有实际实现，不是只有界面。主要缺口在数据一致性、失败执行证据、长期历史检索，以及首次真实使用配置。

“功能页面齐全”“主流程测试通过”“连续使用证明有价值”是三个不同层次。现有 16 项测试通过，但本次额外复现了正常主流程测试没有覆盖的问题，因此不能沿用旧验收记录得出“已经全部完成”。

本次核对产品文档、全部业务页面、Python API/存储/订阅逻辑、桌面启动与打包逻辑、现有测试、本机配置与两个真实数据库的元数据。在临时数据库中进行边界复现，并在隔离浏览器实例中验证建任务、确认计划、完成任务及查看日报。不是完整安全审计或全平台兼容性验收。

真实数据库使用 SQLite 只读连接检查；没有创建真实任务、调用真实 Agent 执行任务、刷新真实订阅或写入真实 Obsidian。临时服务关闭自动化，防止审查数据触发模型调用。新模块和业务修复均未实施。

## 1. 用什么目标衡量完成度

依据 [V0.1 产品设计](Personal-OSV0.1产品设计.md) 与 [既有实施计划](2026-09-23_mvp-implementation-plan.md)，当前 MVP 验证的是：

> 每天从 Personal OS 开始工作，一天结束时，系统能准确呈现当天做过的事。

主闭环：计划 → 执行/委派 → 审核 → 日报确认 → 次日上下文。

连续使用 7 天的原定验收指标：

1. Personal OS 成为每天开始工作的第一入口。
2. 昨日记录能进入简报/历史，不必主动去 Obsidian 寻找日报。
3. 至少 80% 的 Agent 任务从 Personal OS 发出并返回。分母需要同时计入在外部工具发出的 Agent 任务；应用目前不会自动测量该比例。

目前没有真实任务、日报或连续使用数据，以上指标全部尚未验证。

你的长期目标是持续使用的个人工作台。现有项目、任务、决策、事件和知识提案可以继续作为基础；学习记录、点子记录、规则领悟目前没有独立对象或使用流程。它们还未定义，不应被算作本轮 V0.1 的欠账，也不能拿目前的 Settings 个人规则当作“规则领悟模块已经实现”。

## 2. 已经可以做到什么

| 能力 | 已实现行为 | 实际边界 |
|---|---|---|
| macOS 客户端 | 独立窗口、自动启动本地 API、SQLite 持久化、退出时关闭服务 | 仍依赖本机 Python 3.12+；不是独立运行时安装包 |
| Today | 从现有任务生成本地建议或 Codex 建议；确认计划后显示今日任务 | AI 最多选 3 个已有任务；不是任意目标拆解；计划排序/调整存在 R02、R06 问题 |
| Tasks | 建立、编辑、优先级、截止日期、项目关联、人工完成、Agent 执行 | 没有任务归档、删除、完成后重开或完整的人工状态转换入口 |
| Projects / Decision | 项目阶段与状态、工作目录、决策记录及编辑、项目脉搏 | 脉搏是保存的文本；已有内容不会随每次进展自动更新 |
| Agent / Review | 调用本机 Codex、取消、结果返回审核、继续修改/重跑、确认后完成 | 直接修改指定工作目录；审核不是文件改动的提交闸门；产物仅列文件名和变更类型，没有内置 diff/回滚 |
| Daily Log / History | 事件生成日报、手动修改、可选 AI 整理、确认封存、按日查看 | 草稿会过期；历史事件窗口限制为最新 1,000 条；不支持周/月/年视图 |
| Intelligence | RSS/Atom、关键词包含/排除、每日上限、去重、来源及原因、收藏/忽略、转任务 | 不是互联网通用搜索；反馈没有驱动推荐学习；时间与错误展示存在问题 |
| Obsidian | 发现当天 Markdown 文件修改、记录路径与时间；知识提案经批准新建 Markdown | 不读取笔记正文用于知识理解，不同步全文/标签/双链，不导入现有日报，不覆盖同名笔记 |
| Personal Rules | 自然语言规则增删改、启用/禁用；部分 AI 生成读取规则 | 属于部分提示上下文，不是统一规则执行引擎；不能假设所有按钮和 Agent 都遵守 |
| 外观与搜索 | 三套固定主题按时间/手动切换、称呼可改；按标题搜索任务和项目 | 未实现任意角色/背景配置；不搜索历史、正文、笔记；没有完整 Ask 助手 |

## 6. 现在怎么开始使用

### 第一次：先跑通一个真实小闭环

1. 打开现有应用。终端也可以执行：

   ```sh
   open '/Users/geminchen/My-Item/Personal-OS/build/Personal OS.app'
   ```

2. 进入 Settings，核对 Obsidian 路径、称呼及主题。修改 vault 后点击页面中的“保存设置”。Codex 已登录，但 Settings 的运行时说明本身不是连通性自检结果。
3. 进入 Projects，新建一个真实项目，写清目标和当前阶段。如需 Agent，填该项目的实际本地目录。目录是 Codex 实际读写的地方，不要随意填包含无关材料的大目录。
4. 进入 Tasks，先建 2–3 个今天真要做的小任务。每个任务写出可核对的完成标准。开始可选“我自己”，无需先配置情报、规则或 AI 执行。
5. 进入 Today，检查建议，必要时移除不做的任务，点击“确认今日计划”。当前不依赖 AI 也能完成这一步。额外任务在 Tasks 选中后点“加入今天”；确认后的顺序/移除限制见 R06。
6. 做完一个人工任务，在 Today 点击“完成”或 Tasks 点击“确认完成”。仅外部软件里的活动不会自动变成完成事件，需要在这里确认或在日报中补记。
7. 当天收尾时生成日报，进入 History，核对正文与时间线。若此前已自动/手动生成草稿，先“修改日报”，或使用“AI 整理”后再次核对，避免 R01 的旧内容。把失败/阻塞任务也手动补记进去。
8. 确认无误再点“结束今天”。当前已确认日报不能重新编辑，应在封存前完成纠偏。第二天再看昨日记录和未完成任务。

### 第二次：验证一个小型 Agent 任务

1. 确认项目的本地工作目录有效；首个任务选择范围小、结果容易核对的内容。
2. Tasks 新建/编辑任务，执行方式选 Agent，并把必须遵守的约束直接写入“描述与完成标准”（当前 R05 尚未修复）。
3. 点击“交给 Codex”。这才会启动执行；仅把执行方式设为 Agent 不会自动执行。
4. 保持应用运行。关闭最后一个窗口会退出应用并中断执行。失败任务可在“已阻塞”筛选中查看错误，并检查工作目录的实际变更。
5. 完成后去 Review 检查结果与文件；文件已经被改动。满意后“确认完成”，否则“继续修改”并写具体要求，或“重新执行”。这里没有内置代码 diff/回滚。
6. 值得保留的成果，在已完成任务中点击“沉淀为知识”，填写内容。Review 中再次选择“写入 Obsidian”，才会在 vault 的 `Personal-OS/` 下创建文件；重名需要修改标题。

### 第三次：配置情报与少量规则

在 Intelligence 新建一个频道，填写真实 RSS/Atom URL（不是普通网站首页）、简短关注关键词、排除关键词、每日上限。选中频道后点击“刷新来源”。当前失败展示不充分，空结果不一定意味着没有新消息。不要依赖“今日精选”标题判断每条内容都是今天发布。

RSS 自动抓取的条目默认没有项目关联。“深入研究”只会创建 Agent 任务，不会立即研究；先到 Tasks 关联具有工作目录的项目，再点击“交给 Codex”。“创建任务”会打开可编辑表单，可在那里选择项目并补充原始链接和完成标准。

个人规则可以先录入 2–3 条，用于 AI 简报/日报参考；不要把规则开关当作所有执行行为的强制保护，也不要把它当作独立的个人领悟记录模块。

### 自动化和数据保护

自动化依赖应用保持运行。08:00–19:59 会尝试当天订阅刷新和简报；项目脉搏只对尚无脉搏的活跃项目尝试生成。20:00 后会为没有日报的当天生成基础草稿；不会替你确认，不保证自动用模型精炼，也不会在应用退出后继续运行。

试用期间，最可靠的方式是自己在收尾时核对日报。正式长期依赖前，应补 R01–R05、R09 及可验证备份恢复。当前手动备份需退出应用并确认后台停止后复制整个 `~/Library/Application Support/Personal OS/` 目录，避免运行中只复制 SQLite 主文件而漏掉 WAL。

## 7. 离 MVP 还有多远

不以页面数量或随意百分比表示完成度；当前缺少的工作可分为三道门槛：

| 门槛 | 当前判断 | 通过条件 |
|---|---|---|
| 能开始用 | 已基本达到 | 用正式客户端建真实项目和少量任务，完成一个人工闭环；Agent/RSS 另做真实连接验证 |
| 能信任日常记录 | 尚未达到 | 优先修复 R01–R05；计划顺序和订阅结果不误导；长期使用前解决 R09、备份恢复 |
| MVP 方向成立 | 尚未开始验证 | 连续 7 天达到第一入口、昨日记录可用、80% Agent 任务闭环三条指标；记录实际遗漏和使用阻力 |

建议下一步是一轮稳定性修复与首次配置，然后进入 7 天试用。测试不能替代这 7 天；这也不是承诺“再写几天代码就一定完成”。无须先实现多 Agent、完整笔记编辑器、移动端、日历或三个未定模块。

试用每天只需记四件事：是否从这里开始工作；已完成事项有无遗漏/误报；Agent 任务从哪里发出及是否回到 Review；有多少次因为功能缺口不得不离开。

## 8. 长期个人工作台方向

当前基础已经超出单纯 AI 运行看板：人工任务、项目决策、每日记录和知识提案都不依赖 Agent。适合保留这条主线，先让事实记录可信。

学习记录、点子记录、规则领悟都可能成为非任务型内容；目前的模型没有直接承载它们。尤其需要区分“我领悟了什么”和“我要求系统怎么做”，不能把所有内容塞进 Settings 的 Personal Rules 或假装成待办任务。这是后续产品定义的约束，不是本次模块方案。

等真实使用提供证据后，再判断这些记录如何捕获、与项目/任务关联、如何找回及复用。本轮只保留方向，没有新增页面、数据库对象、连接器或模块。
